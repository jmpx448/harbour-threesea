# Audit of the 2026-10-30 changes (security and quality)

What this covers: everything between the state before that day's changes and the commit that carries this file — the
cover's name, media of our own messages from another device, the emulator's demo data, chat
export, the file-size setting, notes groups, editing a photo before sending, the Harbour
validator script, and French.

How it was checked:

- the whole diff read line by line, with CLAUDE.md §7 in hand;
- `scripts/check.sh`: private data, logging rule, `cargo fmt`, clippy (with **and** without the
  `demo` feature), 221 tests, `cargo audit` (306 crates, nothing);
- every new feature driven in the emulator on the demo data;
- the built library searched for the demo code to prove it cannot reach a phone;
- the photo editor checked against a picture that carries an EXIF orientation flag, the way a
  phone camera writes them.

Eight findings, all fixed in this pass. Four of them would show on a phone (S2, Q1, Q2, Q4);
the demo ones are emulator-only, because that code is not in a device build — but S1's traffic
was real, sent by the project's test identity.

## S1 — The demo data made the app send test messages (serious, fixed)

The seeder wrote a demo message in state "pending". `Store::pending_outgoing()` returns
**every** outgoing message in that state, and the connection sends them all after each connect
(`send_pending`, right after the handshake). So the emulator — which carries the project's own
test Threema ID, a registered identity with its own licence — repeatedly sent a few test messages to
`DEMO0008`, a made-up ID, until this was fixed. The log shows it: five `encoding outgoing message feature_mask=255` lines
(255 is the demo contacts' made-up feature mask) right after the demo data was first added.

Opening a demo chat also sent a read receipt to such an ID, and writing in one would have sent
a typing indicator.

Fixed: the demo data contains nothing in a sendable state (a delivered and a failed message
show those states instead), and every demo contact carries "never send" for read receipts and
typing indicators, so nothing goes out by itself. A deliberate send in a demo chat still fails,
as it must — nothing is behind those IDs. `demo_data_fills_and_clears_the_chat_list` now
asserts that `pending_outgoing()` is empty after seeding and that both policies are set.

## S2 — The photo editor ignored the EXIF rotation (moderate, fixed)

`ThreeseBackend::editPhoto` loaded the picture with `QImage(path)`, which does not apply the
EXIF orientation, while `FilePreparer` (which prepares everything we send) explicitly does
(`setAutoTransform(true)`). A photo from a phone camera is almost always stored rotated with
an orientation flag, so the cut would have been taken from a differently-oriented picture and
the result sent sideways. The emulator missed it at first because the test picture had no such
flag.

Fixed on both sides: `editPhoto` reads through `QImageReader` with `setAutoTransform(true)`,
and the editor's view — plus the attachment preview in the chat — set `autoTransform: true`
(QML's `Image` leaves the rotation alone unless asked). Checked with a picture stored rotated
with orientation 6: the editor shows it upright, the frame over the red corner produces a file
that is 98 % red, 266 × 196, without EXIF.

## Q1 — Cropping barely followed the finger (fixed)

Two causes. The dialog's own left/right swipe (accept, cancel) took the drag away after a few
pixels — a drag towards the corner closed the editor instead of cutting. And the grips measured
the drag inside themselves, while they move with the frame, so the movement chased its own
tail. Fixed with `preventStealing: true` on the frame and the grips, and by putting the corner
where the finger is in the picture's coordinates (`mapToItem`). Checked on screen.

## Q2 — The export held media and long chats twice in memory (fixed)

Every media file was copied once more on its way into the archive, and the chat's messages were
collected page by page and then concatenated into a second list. On a phone, a 100 MB video
would have meant 200 MB. The data now moves into the compressing task, and the pages are read
backwards and written forwards without a second copy.

## Q3 — A message's time could overflow the export (fixed)

`created_at` comes from the sender, so it can be anything; adding the time-zone offset could
overflow (panic in a debug build, a wrapped number in a release build). It saturates now.

## Q4 — The editor's result could land on the wrong attachment (fixed)

The edited picture was put back by the index it came from, and a failure was silent. It is now
matched by path (if the attachment was dropped meanwhile, the copy is removed instead of left
behind), and a failure says so.

## Q5 — The demo entries froze the settings page (fixed)

"Remove demo chats" used a `RemorseItem`. That kind reparents itself over the item it counts
down on, with `anchors.fill` — and the item sits in a `Column`, which then refuses to lay out
at all ("QML Column: Cannot specify … fill … Column will not function" in the journal). The
page stopped scrolling and looked frozen, while the app itself was running normally. It uses
the page-level `RemorsePopup` now, as LogPage's "Clear log" does. No other page in the app has
a `RemorseItem` outside a list row.

## S3 — The demo entry was hidden in every build, not absent from it (fixed)

Raised by the user after reading this audit: the core's demo command was behind a Cargo feature
and provably not in a device build, but the **entry in the settings page was in every build's
QML**, merely hidden by `backend.emulator`, and its four texts were in the translation
catalogues that ship. Hiding is not absence: anyone reading the package can see it, and a
mistake in the condition would show it.

The first attempt moved the entry into a file installed only by `qmake CONFIG+=demo` — but
the package still carried the `Loader` line and a `demoData` property in the binary. "Almost
absent" is not absent, so the demo data lost its user interface altogether: it is asked for
over D-Bus (`scripts/emulator-demo.sh` → `DBusInterface::demoData` → the core's command), and
each of those parts is compiled only into an emulator build (`CONFIG+=demo`, Cargo feature
`demo`, both set for i486 alone by the build scripts). The four texts left the translation
catalogues with it (789 now). Checked on the built packages: the phone's binary, its QML and
its `.qm` files contain no trace.

CLAUDE.md §10 now carries this as a standing rule: nothing for testing ships, and the package
is to be checked rather than assumed.

## Accepted properties, not defects

- **The demo command's D-Bus method takes no token**, unlike Reply and Mark as read. Those act
  on real chats in every build; this one only exists in an emulator build, where it seeds or
  removes made-up data.


- **The export directory comes from the UI** (`StandardPaths.download`); the core does not check
  it, as with the log package and "Save to Downloads". Inside the sandbox this is the app's own
  reach.
- **The size limit trusts the sender's stated size.** A sender who lies can still only make us
  fetch what the blob cap allows (100 MiB), and the preview is never held back. Android has the
  same property.
- **Password fields in QML are ordinary strings**, not wiped — the existing pattern for every
  password in the app.
- **Demo contacts carry a made-up public key.** They exist only in the emulator build; writing
  to one fails, which is the honest outcome.
- **The first start after this update may fetch a backlog**: media sent from Threema Desktop
  that was never downloaded now arrives by itself. On a phone with a long Desktop history that
  can be a few dozen MB — worth being on Wi-Fi for that first start, or setting
  Settings → Media and storage → File size first.

## What the emulator could not say

The language (the image has only the C and POSIX locales), the photo editor on real camera
photos beyond the EXIF check done here, the export of a chat with large videos, battery and
reconnect behaviour, and anything about the earpiece, the proximity sensor or hardware video.
Those are in `docs/voice-video-device-checklist.md` (sections J–P).
